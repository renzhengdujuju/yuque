先确认一下 IP：你写的是 **node1 192.168.75.10、node2 192.168.75.10、node3 192.168.75.30**，这里 node1 和 node2 重复了，应该是 **node2 为 192.168.75.20** 对吧？下面先按这个来讲。

整体流程可以按这条线走：

**系统准备 → MySQL 主从 + 半同步 → Redis 主从 + 哨兵 → MongoDB 副本集 → 监控脚本 → 故障演练。**

### 1. 先做系统准备
三台机器都要执行：

```plain
systemctl stop firewalld
systemctl disable firewalld
setenforce 0
```

或者更规范一点，开放端口：

|  |  |
| --- | --- |
| **服务** | **端口** |
| MySQL | 3306 |
| Redis | 6379 |
| Redis Sentinel | 26379 |
| MongoDB | 27017 |

三台机器之间要能互相 ping 通：

```plain
ping 192.168.75.10
ping 192.168.75.20
ping 192.168.75.30
```

### 2. MySQL 主从 + 半同步复制
**Node1 192.168.75.10 作为 MySQL 主库。**

`/etc/my.cnf`：

```plain
[mysqld]
server-id = 1
log-bin = mysql-bin
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON
rpl_semi_sync_source_enabled = 1
rpl_semi_sync_source_timeout = 10000
```

解释：

- server-id mysql实例的唯一标识，主从复制里每一个id不一样
- 开启binlog，并指定文件前缀为mysql-bin
- 记录模式为ROW模式，会记录每一行数据变化
- 开启GTID复制，GTID会给每个事务分配一个全局唯一id
- 强制GTID一致性检查
- 在主库上开启半同步复制，之前叫master/slave，现在是source/replica
- 半同步的意思就是：主库提交事务时，至少要等一个从库把binlog写入中继日志并返回ack主库才告诉客户端“写入成功”
- 设置半同步复制超时时间，10000表示10秒，如果主库10秒内没有收到从库的ack，自动降级层异步复制，避免一直卡住写请求

主库创建复制用户：

```plain
CREATE USER 'repl'@'192.168.75.20' IDENTIFIED BY 'Repl@123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'192.168.75.20';
FLUSH PRIVILEGES;
```

解释：

- 创建一个名字为repl'@'192.168.75.20的用户，密码为Repl@123
- 给repl用户授予replication slave权限，这个权限只允许他读取主库的binlog，不需要insert、select等其他权限
- 刷新权限表，让刚刚创建的用户和权限生效

安装半同步插件：

```plain
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
```

解释：

- INSTALL PLUGIN ：表示要下载插件
- rpl\_semi\_sync\_source：插件名，表示“复制半同步源端插件”；主从库不一样，从库rpl\_semi\_sync\_replica
- SONAME 'semisync\_source.so'：指定插件的共享库文件，linux下是semisync\_source.so
- 这个插件的作用：  
  1.事务提交时，等待至少确认一个从库确认收到binlog文件

2.收到从库的ACK后，才向客户端返回成功

3.如果超时没有收到ACK，将会降级成异步复制，避免一直阻塞

- 安装好只是第一步，还要启用它：  
  SET GLOBAL rpl\_semi\_sync\_source\_enabled = 1;
- 从库也要安装对应的插件

**Node2 192.168.75.20 作为 MySQL 从库。**

`/etc/my.cnf`：

```plain
[mysqld]
server-id = 2
log-bin = mysql-bin
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON
rpl_semi_sync_replica_enabled = 1
```

安装插件：

```plain
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
```

配置主从：

```plain
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.75.10',
  SOURCE_USER='repl',
  SOURCE_PASSWORD='Repl@123',
  SOURCE_AUTO_POSITION=1;

START REPLICA;
```

解释：

- 配置从节点连接的主节点信息旧版本是change master to ，新版本是change replication source to
- 设置主节点ip，连接主节点的用户及密码
- 开启这个GTID自动定位，因为前面都开启了gtid\_mode=ON enforce\_gtid\_consistency=ON（开启GTID复制，和强制GTID一致性检查），他会自动根据GTID判断自己已经同步到哪个事务，然后接着从主库拉取后面的事务
- 启动从库复制

执行后从库有启动两个线程：

I/O线程：从库去拉取主库的binlog

SQL线程：拉取来的binlog，将信息放入从库

验证：

```plain
SHOW REPLICA STATUS\G
```

确认 `Replica_IO_Running` 和 `Replica_SQL_Running` 都是 `Yes`。

### 3. Redis 主从
这里建议：

- **192.168.75.10：Redis 主**
- **192.168.75.20：Redis 从**
- **192.168.75.30：Redis 从**

主节点 `redis.conf`：

```plain
bind 0.0.0.0
protected-mode no
port 6379
requirepass Redis@123
masterauth Redis@123
appendonly yes
appendfsync everysec
maxmemory 512mb
maxmemory-policy allkeys-lru
save 900 1
save 300 10
save 60 10000
aof-use-rdb-preamble yes
```

解释：

- 监听所有网卡，允许远程连接，生产环境建议换成内网，比如 bind 192.168.75.10
- 关闭保护模式，保护模式会关闭外部连接
- 端口
- 客户端访问密码
- 主从复制时，从节点通过密码连接主节点，主节点配置这个是为了当他变成从节点的时候也可以通过这个连接新主
- 开启AOF持久化，所有命令会追加到AOF文件
- 每秒刷盘一次，性能和安全比较均衡，宕机最多丢失1秒数据
- 这是 RDB 快照触发条件：

- 900 秒内有 1 次写操作 → 触发快照
- 300 秒内有 10 次写操作 → 触发快照
- 60 秒内有 10000 次写操作 → 触发快照

- 开启混合持久化
- redis最多用512M，超过会触发淘汰机制
- 内存满了，从所有key中挑选最近最少使用的

从节点 `redis.conf`：

```plain
bind 0.0.0.0
protected-mode no
port 6379
requirepass Redis@123
masterauth Redis@123
replicaof 192.168.75.10 6379
appendonly yes
appendfsync everysec
maxmemory 512mb
maxmemory-policy allkeys-lru
save 900 1
save 300 10
save 60 10000
aof-use-rdb-preamble yes
```

解释：

- 和主节点相比，多了一行 `replicaof 192.168.75.10 6379`
- 这一行是 **从节点身份声明**，告诉 Redis：“我是从节点，我的主节点是192.168.75.10:6379”。

启动后验证：

```plain
redis-cli -a Redis@123 INFO replication
```

可以在主节点和从节点执行：

主节点应显示

- `role:master`：说明当前是主节点
- `connected_slaves:2`。

从节点应显示

- `role:slave`：说明当前是从节点

- `master_link_status:up`：和主节点连接正常；如果是 `down`，说明复制断了
- `slave_repl_offset`：从节点已经同步到的复制偏移量

### 4. Redis 哨兵
哨兵是独立于 Redis 数据进程的监控进程，生产环境通常部署 3 个哨兵实例，避免单点故障。

三台机器各跑一个哨兵，端口都用 `26379`。

`sentinel.conf`：

```plain
port 26379
daemonize yes
sentinel monitor mymaster 192.168.75.10 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 180000
sentinel parallel-syncs mymaster 1
sentinel auth-pass mymaster Redis@123
```

解释：

- 端口
- 以守护进程方式启动
- 告诉哨兵：监控名为mymaster的主节点，地址是192.168.75.10 6379 ，2是quorum；这里2表示：至少两个哨兵认为主节点挂了，才会真正判断主节点下线并触发故障转移功能
- 主节点5000毫秒也就是5秒内没有响应，则当前哨兵把他标记为“主观下线”
- 故障转移超时时间，如果这个时间内故障转移没有完成，认为本次故障转移失败
- 故障转移后，允许一个从节点去同步新主节点，设置为1避免新主节点压力大
- 哨兵连接主从节点时需要的密码，得和requirepass里面一致

启动顺序：**先 Redis，后哨兵**。

```plain
redis-sentinel /etc/redis/sentinel.conf
```

或者

```plain
redis-server /etc/redis/sentinel.conf --sentinel
```

验证：

```plain
redis-cli -p 26379 INFO sentinel
```

确认 `slaves=2`、`sentinels=3`。

然后可以停掉 `192.168.75.10` 的 Redis，看哨兵是否自动把某个从节点提升为主。

### 5. MongoDB 副本集
三台机器都安装 MongoDB，配置文件**mongod.conf** 里加上：

```plain
storage:
  dbPath: /var/lib/mongo

net:
  port: 27017
  bindIp: 0.0.0.0

replication:
  replSetName: rs0
```

主要就是

- 存储设置

- 数据文件存放目录/var/lib/mongo

- 网络设置

- 端口 绑定的ip

- 日志设置

- 日志格式和日志路径

- 副本设置

- rs0是副本集的名称，所有节点必须保持一致
- 只有配置这一行，MongDB才会启用副本集模式
- 不配置的话MongDB就是单主机模式，不能主从选举和数据同步

分别启动 mongod：

```plain
systemctl start mongod
```

在任意一台机器进入 mongo shell：

```plain
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "192.168.75.10:27017" },
    { _id: 1, host: "192.168.75.20:27017" },
    { _id: 2, host: "192.168.75.30:27017" }
  ]
})
```

等待几秒后执行：

```plain
rs.status()
```

确认有一个 `PRIMARY`，两个 `SECONDARY`。

### 6. Shell 监控脚本
可以在 **Node1** 上写一个监控脚本，比如 `/opt/monitor/check.sh`：

```plain
#!/bin/bash

# 检查 Redis 是否存活
redis-cli -h 192.168.75.10 -a Redis@123 ping | grep -q PONG
if [ $? -ne 0 ]; then
  curl -X POST "钉钉Webhook地址" \
    -H "Content-Type: application/json" \
    -d '{"msgtype":"text","text":{"content":"Redis主节点异常"}}'
fi

# 检查 MySQL 连接数
CONN=$(mysql -uroot -p'密码' -e "SHOW STATUS LIKE 'Threads_connected'" | awk '{print $2}')
if [ "$CONN" -gt 100 ]; then
  curl -X POST "钉钉Webhook地址" \
    -H "Content-Type: application/json" \
    -d '{"msgtype":"text","text":{"content":"MySQL连接数过高: '$CONN'"}}'
fi
```

解释：

reids健康检查

- 连接到 Redis 主节点执行 `ping`，正常会返回 `PONG`。`grep -q PONG` 只判断是否包含 `PONG`，不输出内容。

- `$?` 是上一条命令的退出码。`-ne 0` 表示“不等于 0”，也就是 **ping 失败或没返回 PONG** 时进入告警分支。
- 通过钉钉机器人 Webhook 发送文本告警。

Mysql连接数检查

- 登录 MySQL，查询当前连接数 `Threads_connected`，再用 `awk` 取出数值。
- 如果连接数大于 100，就触发告警。

加到 crontab：

```plain
crontab -e
```

```plain
* * * * * /bin/bash /opt/monitor/check.sh>> /var/log/check.log 2>&1
```

每 1分钟执行一次。

### 7. 最后做一轮验证
按这个顺序测：

1. MySQL 主库写数据，从库能查到；
2. Redis 主节点写 key，从节点能读到；
3. 停掉 Redis 主节点，哨兵自动切换；
4. 停掉 MongoDB Primary，副本集自动选举新主；
5. 触发慢查询或连接数告警，钉钉能收到消息。

读 QPS 提升主要靠 MySQL 读写分离，写请求走主库，读请求通过代理路由到从库，读流量被分散后主库压力下降。Redis 命中率通过设置 maxmemory 和 allkeys-lru 淘汰策略，同时配合热点数据缓存、合理 TTL、防穿透和预热，命中率稳定在 95% 以上。哨兵负责自动故障转移，主节点故障后由哨兵投票选举新主，整个过程控制在 10 秒内。慢查询通过慢查询日志和 EXPLAIN 定位，再按最左前缀原则添加联合索引，使扫描行数下降，慢查询从日均 500+ 降到 50 以下。
